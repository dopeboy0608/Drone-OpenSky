# Phase 0 Research: 모바일 뷰포트 하단 플로팅 요소 노출 수정

## 컨테이너 크기 단위: `100vh`/`100vw` → `100dvh`/`100dvw`

- **Decision**: `src/pages/MapPage.tsx`의 `h-screen w-screen`(Tailwind, `100vh`/`100vw`)을 `h-dvh w-dvw`(`100dvh`/`100dvw`, dynamic viewport)로 교체한다.
- **Rationale**: iOS Safari/Android Chrome 등 모바일 브라우저는 스크롤 시 주소창/도구모음이 나타났다 사라지며 실제 보이는 영역(viewport)이 변한다. `100vh`는 "가장 작은(주소창이 펼쳐진) 상태"의 레이아웃 뷰포트 높이로 고정되는 경우가 많아, 주소창이 접히면 그만큼 화면 하단에 실제로는 보이는데도 컨테이너가 못 채운 영역이 생기거나, 반대로 컨테이너가 실제 보이는 영역보다 커져 하단 요소가 화면 밖으로 밀리는 문제가 발생한다(브라우저/버전별 100vh 처리 방식 차이가 이 문제의 근본 원인). `100dvh`는 브라우저가 주소창 상태 변화에 따라 실시간으로 재계산하는 동적 뷰포트 단위로, 항상 "지금 실제로 보이는" 높이를 반환해 하단 플로팅 요소가 화면 밖으로 밀리지 않는다.
- **Alternatives considered**:
  - **JS로 `window.visualViewport` 구독해 높이를 state로 관리**: 더 세밀한 제어가 가능하지만 리스너 등록/해제, resize 이벤트 스로틀링 등 부수효과 코드가 늘어난다. CSS만으로 해결 가능한 문제에 JS 상태를 도입하는 건 과설계이며, spec FR-005(CSS 수준 해결)와도 맞지 않아 기각.
  - **하단 요소에 `env(safe-area-inset-bottom)` 추가**: 노치/홈 인디케이터 대응 기법으로, 이번 문제(주소창에 의한 동적 뷰포트 변화)와는 원인이 다르다. 필요성이 확인되지 않아 이번 스코프에서는 제외하되, 추후 실기기 검증에서 노치 기기 겹침이 발견되면 별도로 추가 검토.
  - **최소 지원 브라우저 낮춰서 `100vh` 유지 + 하단 padding만 늘리기**: 근본 원인을 해결하지 못하고 기기별로 다른 여백 값을 하드코딩해야 해 유지보수성이 떨어진다. 기각.
- **호환성**: `dvh`/`dvw`는 Tailwind CSS v3.4+에서 기본 유틸리티로 제공되며 이 프로젝트는 v4.3을 사용 중이라 추가 설정 없이 사용 가능. 구형 브라우저(동적 뷰포트 단위 미지원)에서는 `dvh` 값이 무시되지 않고 `vh`와 동일하게 동작하는 것이 CSS 스펙 동작이므로, 기존 대비 더 나빠지지 않는다(점진적 개선, 폴백 자연 처리).

## Kakao 지도 기본 축척 표시

- **Decision**: 별도 코드 수정 없음. 컨테이너(`MapView`) 크기가 `h-full w-full`로 부모(`MapPage`)를 정확히 채우도록 부모 크기만 고치면, Kakao Maps SDK가 자체적으로 컨테이너 내부에 축척을 렌더링하므로 함께 해결된다.
- **Rationale**: `MapView.tsx`의 `KakaoMap`은 이미 `style={{ width: '100%', height: '100%' }}`로 부모를 채우고 있어, 축척이 화면 밖으로 밀리는 원인은 SDK 자체가 아니라 상위 컨테이너(`MapPage`)의 크기 계산 문제로 확인됨.
